# Frontend — Keyword Suggest & Intent Analyzer

Plain HTML/CSS/JS. **No build tooling, no npm, no framework.** The admin
signs in with a username and password, types a seed topic, and runs an
analysis; the backend returns the raw keyword data and an AI-generated
Markdown report, which this UI renders, filters, and exports.

It is deployed as a **Render Static Site**, entirely separate from the
backend service. See the [root README](../README.md) for the overall
architecture.

## Files

| File | Purpose |
|---|---|
| `index.html` | Markup: sign-in gate, topic form, results tabs. |
| `styles.css` | All colour/spacing/type values are CSS custom properties on `:root`, with a `prefers-color-scheme: dark` override. System fonts only. |
| `app.js` | All application logic. One rendering path shared by real and mock runs. |
| `config.js` | Runtime config: `API_BASE_URL`. **Generated by `build.sh` on deploy.** |
| `build.sh` | Render build step: writes `config.js` from the `API_BASE_URL` env var. |
| `mock-response.json` | Fixture for mock mode. |

The only external dependencies are `marked` and `DOMPurify`, loaded from
jsDelivr at pinned versions with SRI hashes. There are no font imports.

## Configuration

One setting, in `config.js`:

```js
window.APP_CONFIG = {
  API_BASE_URL: "http://localhost:8000"
};
```

- `API_BASE_URL` is the **backend service's origin**, with no trailing
  slash. Every API call is `API_BASE_URL + "/api/..."`.
- An empty string (`""`) means "same origin as this page" — useful only if
  you ever put both behind one host.

**The committed value is the local-development default.** On Render it is
overwritten during the build, so editing this file does not change a
deployment. `build.sh`:

- reads `API_BASE_URL` from the environment;
- strips a trailing slash, and promotes a bare hostname to `https://<host>`
  (Render's `fromService: property: host` yields a hostname with no scheme);
- **fails the build** if `API_BASE_URL` is unset, rather than shipping a UI
  that silently calls `localhost`.

## Running locally

The backend must be running first — see [backend/README.md](../backend/README.md).

```bash
cd frontend
python3 -m http.server 5173
```

Open **http://localhost:5173**.

That is all the configuration needed: `config.js` already points at
`http://localhost:8000`, and the backend in `MODE=dev` accepts any
`http://localhost:*` origin.

> Use a real HTTP server, not `file://`. Opening `index.html` from disk makes
> the page's origin `null`, which CORS rejects and which breaks
> `sessionStorage`. Any static server works — `python3 -m http.server`,
> `npx serve`, VS Code Live Server — only the port matters, and only because
> it has to differ from the backend's.

### Testing it end to end

With both services running, open http://localhost:5173 and check:

1. **Sign-in gate** — wrong credentials show "Invalid username or password.";
   correct ones (from `backend/.env`) land you on the topic form with the
   remaining search quota shown in the header.
2. **A run** — enter a topic, press *Run Analysis*. An elapsed-seconds
   counter runs; results arrive with the AI report and the raw keywords.
3. **Both result tabs** — *AI report* renders Markdown; *Raw keywords*
   toggles between grouped-by-source-query and a flat unique list, and the
   filter box narrows both.
4. **Exports** — *Download report (.md)*, *Download keywords (.csv)*, and the
   two copy buttons.
5. **Log out** — returns to the gate; reloading does not restore the session.

### Mock mode — no backend at all

```
http://localhost:5173/index.html?mock=1
```

`?mock=1` bypasses the sign-in gate entirely and, on *Run Analysis*, waits 6
seconds (simulating a real run) before rendering `mock-response.json` through
the exact same code path as a real response. Useful for UI work with no API
key and no backend running. Mock mode ignores `API_BASE_URL` completely.

## Deploying to Render

Deployed by the root `render.yaml` as `keyword-analyzer-web`, or manually:

| Setting | Value |
|---|---|
| Type | Static Site |
| Root directory | `frontend` |
| Build command | `./build.sh` |
| Publish directory | `.` |

Environment variables:

| Variable | Required | Value |
|---|---|---|
| `API_BASE_URL` | yes | The backend service's origin, e.g. `https://keyword-analyzer-api.onrender.com`. A bare hostname also works. |

The blueprint sets this automatically from the backend service's host, so
with a blueprint deploy there is nothing to configure.

**After changing `API_BASE_URL`, redeploy** — `config.js` is generated at
build time, so the new value only takes effect on a rebuild.

Also make sure the backend's `ALLOWED_ORIGINS` contains this site's URL, or
every call will fail CORS.

### Verifying a deploy

```bash
curl https://<web-host>/config.js
```

should print the generated file naming your backend's origin. If it still
says `localhost`, the build step did not run.

## How auth works here

1. The gate posts `{username, password}` to `POST /api/login`.
2. The backend returns `{"ok": true, "access_key": "<token>"}`.
3. **Only the token** goes into `sessionStorage` (key `kria_access_key`) —
   never the password.
4. Every authenticated call sends `X-Access-Key: <token>`.
5. Any `401` clears the stored token through a single `clearSession()` helper
   and returns the user to the gate with an explanatory message.
6. *Log out* clears the local session immediately and calls `POST /api/logout`
   best-effort to invalidate the token server-side.

No `localStorage` is used anywhere.

## Notable implementation choices

- **Markdown safety.** `analysis_markdown` always goes through
  `marked.parse()` then `DOMPurify.sanitize()` before touching the DOM. If
  either library fails to load (network, SRI mismatch), a visible banner says
  so and the report falls back to plain text via `textContent` — never raw
  HTML.
- **Client-side run timeout.** 180 seconds via `AbortController`. The
  *Cancel* button aborts the same controller and is distinguished from a
  timeout, so the two show different messages.
- **429 handling.** The form stays disabled and a live countdown runs from
  `retry_after_seconds`; the form re-enables and the quota refreshes the
  moment it reaches zero.
- **Errors never clear existing results.** Error and status messages render
  into a dedicated region above the results, so a failed re-run leaves the
  previous successful results exactly as they were.
- **Accessibility.** Proper tablist semantics with arrow-key navigation,
  `aria-live` regions for status and filter counts, and a skip link.

## API contract

This UI is written against the contract documented in full in
[backend/README.md](../backend/README.md#api-contract). The short version —
all calls carry `X-Access-Key` except `/api/login`:

| Call | Purpose |
|---|---|
| `POST /api/login` | `{username, password}` → `{ok, access_key}` |
| `POST /api/logout` | invalidates the token |
| `GET /api/status` | remaining quota, window, pacing, expected query count |
| `POST /api/analyze` | `{topic}` → the full result payload |

`mock-response.json` is a valid `/api/analyze` response and is validated
against the backend's response model by the backend test suite, so the
fixture cannot silently drift from the real contract.
