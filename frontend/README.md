# Refract — frontend

**Refract** turns one seed topic into the full spectrum of search intent. This
is the client: plain HTML, CSS and JavaScript. **No build tooling, no npm, no
framework.**

Deployed as a **Render Static Site**, separate from the API service. See the
[root README](../README.md) for the overall architecture.

| **Mark** | A prism: triangle outline with a focal dot at its centroid. Two shapes only, so it stays legible at 16px and in a favicon. |

The metaphor is literal — a prism refracts one beam into a spectrum; Refract
splits one topic into the spectrum of intent behind it. The empty-state
illustration is the same idea drawn out: one beam in, four rays out, each
coloured to match one of the four intent classes in the legend.

## Design system

Everything lives in `styles.css` in three layers: **tokens**, **primitives**
(button, input, chip, alert, menu, tab, panel), then **regions** (gate,
topbar, query bar, metrics, results). Change a token, not a component.

### Type

Three families, loaded from Google Fonts:

- **Instrument Sans** — display. Headlines, metric values, the topic.
- **Inter** — UI. Everything else.
- **JetBrains Mono** — data. Source queries, counts, timers, durations.

Sizes are tokens (`--fs-display-xl` … `--fs-micro`) and headline tracking is
tight (`-0.035em`) so large type reads as set, not as scaled-up body copy.

> **Fonts are the one thing that can fail quietly.** If Google Fonts is
> unreachable — firewall, blocked region, offline — every family falls back to
> a system stack and the layout holds, because sizes and spacing are tokens
> rather than font-dependent. Nothing else about the UI depends on the network
> except `marked`/`DOMPurify`, which degrade to plain text.

### Colour

A warm paper canvas, white surfaces, near-black primary actions, and very
little chroma. Colour is reserved for meaning:

- **Ink** (`--c-ink-1` … `--c-ink-4`) carries emphasis. `--c-ink-4` is the
  **non-text tier** — placeholders, disabled states, icon tints, meter tracks.
  Text never uses it.
- **Accent** (`--c-accent`) marks interaction: focus rings, active states, the
  eyebrow dot, in-progress bars.
- **Intent classes** each own a hue — seed, alphabet, question, commercial —
  used identically in the tags, the intent-mix bar, its legend, and the
  empty-state illustration, so the mapping is learned once.

Dark mode is a full re-token under `prefers-color-scheme`, not a filter. The
primary button inverts (light on dark) rather than staying black.

**All text pairs meet WCAG AA** (4.5:1) in both themes; non-text tiers meet
3:1. Verified by computing ratios from the tokens, not by eye.

### Radius and elevation

`3 / 5 / 8 / 10px`, and nothing else. **No pills.** Separation is by hairline
first; shadow is reserved for things that genuinely float (menus, the query
bar, the frosted-free topbar edge).

### Spacing

A 4px scale (`--s-1` … `--s-13`). Every gap, pad and margin is a token.

### Icons

One inline SVG sprite in `index.html`. Every glyph is drawn in a 20×20 box
with a 1.5 stroke and round caps. Markup carries `viewBox="0 0 20 20"` —
**CSS cannot set a viewBox**, so an icon without it renders clipped.

## Screens and states

Every state is designed, not defaulted:

| State | Treatment |
|---|---|
| **Sign in** | Split: dark brand panel (statement + three facts) beside the form. Collapses to the form alone below 62rem. |
| **Empty** | Editorial headline, an explanation of what a run actually does, example topic chips, and the prism illustration. Fills the viewport instead of leaving a dead zone. |
| **Running** | Stage label (*Collecting…* → *Reading search intent*), an estimated progress bar derived from `expected_queries × pacing`, elapsed seconds, and Cancel. |
| **Results** | Topic as display type, four metrics, the intent-mix bar, then tabs. |
| **Partial** | Amber banner with the exact counts and a disclosure listing every failed query. |
| **Rate limited** | Danger alert with a live countdown bar and `mm:ss`; the form stays disabled until it reaches zero. |
| **Error** | Alert with a plain-English title, cause, and a single next action. **Never clears existing results.** |
| **No matches** | Dedicated in-panel empty state naming the filter term. |

### Results detail

- **Metrics** — unique keywords (with per-query density), queries succeeded
  (with a completion bar that turns amber when partial), source groups, run
  time.
- **Intent mix** — the one piece of real data visualisation. Each keyword is
  counted **once**, under the query type that *first* surfaced it (`types[0]`,
  which preserves discovery order), so the shares total 100%.
- **Intent report** — rendered Markdown at a 68ch measure, with a sticky
  section index built from whatever headings the model actually produced. Wide
  tables get their own scroll container so they never drag the page sideways.
- **Keywords** — grouped by source query (accordions, type tag, count) or flat
  (keyword, its source queries, its type tags). Filter narrows both.

## Configuration

One setting, in `config.js`:

```js
window.APP_CONFIG = {
  API_BASE_URL: "http://localhost:8000"
};
```

- `API_BASE_URL` is the **backend service's origin**, no trailing slash. Every
  API call is `API_BASE_URL + "/api/..."`.
- An empty string means "same origin as this page".

**The committed value is the local-development default.** On Render it is
overwritten during the build, so editing this file does not change a
deployment. `build.sh` reads `API_BASE_URL`, strips a trailing slash, promotes
a bare hostname to `https://`, and **fails the build** if it is unset.

## Running locally

The backend must be running first — see [backend/README.md](../backend/README.md).

```bash
cd frontend
python3 -m http.server 5173
```

Open **http://localhost:5173**.

`python3 -m http.server` prints *"Serving HTTP on 0.0.0.0"*, so browsing to
`http://0.0.0.0:5173` is natural. That works: `MODE=dev` accepts any origin,
and `app.js` re-points a loopback `API_BASE_URL` at whatever host served the
page, so reaching the dev server from a phone on the same Wi-Fi works too.

> Use a real HTTP server, not `file://` — that makes the page's origin `null`,
> which CORS rejects and which breaks `sessionStorage`.

### Mock mode — no backend, no API key

```
http://localhost:5173/index.html?mock=1
```

Bypasses the gate and renders `mock-response.json` through the **same code
path** as a real response, after a 6-second delay so the running state is
exercised too.

### If sign-in says "Could not reach the server"

That message covers every failure the browser reports opaquely, so it does
**not** mean the password is wrong. In order:

1. `curl localhost:8000/api/health` → `{"status":"ok"}`.
2. Open the browser console — a failed call logs the API URL it tried.
3. Check the backend log: `OPTIONS /api/login ... 400` is a rejected CORS
   preflight, not a credentials failure.
4. Check `config.js` names the right origin and port.

By the root `render.yaml`, or manually:

| Setting | Value |
|---|---|
| Type | Static Site |
| Root directory | `frontend` |
| Build command | `./build.sh` |
| Publish directory | `.` |
| Env | `API_BASE_URL` = the backend origin |

**Redeploy after changing `API_BASE_URL`** — `config.js` is generated at build
time. Also ensure the backend's `ALLOWED_ORIGINS` contains this site's URL.

## Auth

1. The gate posts `{username, password}` to `POST /api/login`.
2. The backend returns `{"ok": true, "access_key": "<token>"}`.
3. **Only the token** goes into `sessionStorage` (`refract.session`) — never
   the password.
4. Every authenticated call sends `X-Access-Key`.
5. Any `401` clears the token through one `clearSession()` helper and returns
   to the gate with an explanation.
6. Sign out clears locally, then calls `POST /api/logout` best-effort.

No `localStorage` anywhere. Every `sessionStorage` access is wrapped, so
private-browsing modes that throw do not break the app.

## Accessibility

- AA contrast across both themes, verified from the tokens.
- Visible focus ring on every interactive element (`:focus-visible`, two-tone
  so it reads on any surface).
- Proper tablist semantics with arrow/Home/End roving; menus close on Escape
  and restore focus; click-outside dismisses.
- `aria-live` on quota, run status and filter counts.
- Skip link; `aria-invalid` on failed fields; scrollable tables exposed as
  focusable regions.
- `prefers-reduced-motion` disables animation and smooth scrolling.
- No horizontal scroll from 320px up — verified at 320/390/834/1024/1440.

## Safety notes that still apply

- `analysis_markdown` always goes through `marked.parse()` → `DOMPurify.sanitize()`
  before touching the DOM. If either library fails to load, a banner says so
  and the report falls back to `textContent` — **never** raw HTML.
- Client-side run timeout of 180s via `AbortController`; Cancel uses the same
  controller and is distinguished from a timeout.

## API contract

Documented in full in [backend/README.md](../backend/README.md#api-contract).
All calls carry `X-Access-Key` except `/api/login`:

| Call | Purpose |
|---|---|
| `POST /api/login` | `{username, password}` → `{ok, access_key}` |
| `POST /api/logout` | invalidates the token |
| `GET /api/status` | quota, window, pacing, expected query count |
| `POST /api/analyze` | `{topic}` → the full result payload |

`mock-response.json` is a valid `/api/analyze` response, and the backend test
suite asserts both that it still validates against the response model and that
every `apiUrl("…")` call site in `app.js` maps to a real route — so the fixture
and the client cannot silently drift from the API.
