# Keyword Analyzer — frontend

**Keyword Analyzer** turns one seed topic into the full spectrum of search
intent. This is the client: plain HTML, CSS and JavaScript. **No build
tooling, no npm, no framework.**

Deployed as a **Render Static Site**, separate from the API service. See the
[root README](../README.md) for the overall architecture.

## Design system

Everything lives in `styles.css` in three layers: **tokens**, **primitives**
(button, input, chip, alert, menu, tab, panel), then **regions** (gate,
topbar, query bar, metrics, results). Change a token, not a component.

### Type

Two families, loaded from Google Fonts:

- **Geist** — display and UI. Headlines, metric values, the topic, and every
  label and control. A modern grotesk with a tall x-height and flat
  terminals: it holds at 11px in a table header and still has presence at
  68px, which is what lets one family do both jobs without the interface
  looking like two.
- **Geist Mono** — data. Keywords, source queries, counts, timers,
  durations — anything a user might copy, or compare character by character.

One type system, two weights of voice. Dropping the third family removed a
font request and a seam: display and UI now share a skeleton, so a heading
and the label under it look related rather than merely adjacent.

Sizes are tokens (`--fs-display-xl` … `--fs-micro`) and headline tracking is
tight (`-0.035em`) so large type reads as set, not as scaled-up body copy.

> **Fonts are the one thing that can fail quietly.** If Google Fonts is
> unreachable — firewall, blocked region, offline — every family falls back to
> a system stack and the layout holds, because sizes and spacing are tokens
> rather than font-dependent. Nothing else about the UI depends on the network
> except `marked`/`DOMPurify`, which degrade to plain text.

### Colour

**Black, white and grey.** The palette is a neutral ladder — canvas, surface,
four ink steps, three line weights — and that is nearly all of it.

- **Ink** (`--c-ink-1` … `--c-ink-4`) carries emphasis: 1 for headings and
  data, 2 for body, 3 for labels, 4 for the quietest metadata. **All four
  clear 4.5:1 on both the canvas and white**, so there is no tier that only
  mostly passes and has to be kept away from text.
- **Interaction** (`--c-accent`) is ink. In a monochrome system a near-black
  fill on white is the strongest signal available, which keeps hue free for
  the one place that earns it.
- **Intent classes** are separated by **ink weight and fill, not hue** —
  seed darkest (it is the query the user actually typed), then alphabet,
  question, commercial. Fill and ink are separate tokens on purpose: a
  stacked bar needs the four greys spread as far apart as possible to stay
  readable at 8px, while the same grey as 11px tag text on a tinted chip
  would fall under 4.5:1. The `-ink` steps are the ones tuned against `-bg`.
  Because the classes are distinguished by value rather than colour, they
  also survive greyscale printing and every form of colour blindness.

**One hue exists.** `--c-live` (a restrained orange) appears on exactly two
elements: the run progress bar and the pulsing dot beside *Running*. Nothing
static is ever coloured, so the colour means *this is moving* and nothing
else — which is why a 40-second run reads at a glance from across a desk.

**Light only.** There is no dark palette and no `prefers-color-scheme`
block. The tool is a reading surface, and one well-tuned set of neutrals
beats two mediocre ones; `color-scheme: light` also stops the browser
darkening form controls under a dark OS setting.

**All text pairs meet WCAG AA** (4.5:1), including the four intent tags on
their own tinted backgrounds. Verified by computing ratios from the tokens,
not by eye.

### Radius and elevation

`3 / 5 / 8 / 10px`, and nothing else. **No pills.** Separation is by hairline
first; shadow is reserved for things that genuinely float (menus, the query
bar, the frosted-free topbar edge).

### Spacing

A 4px scale (`--s-1` … `--s-13`). Every gap, pad and margin is a token.

### Icons

One inline SVG sprite in `index.html`. Every glyph is drawn in a 20×20 box
with a 1.5 stroke and round caps. Markup carries `viewBox="0 0 20 20"` —
**CSS cannot set a viewBox**, so an icon without it renders clipped.

## Screens and states

Every state is designed, not defaulted:

| State | Treatment |
|---|---|
| **Sign in** | Split: black brand panel (statement, three facts) beside the form. Collapses to the form alone below 62rem. |
| **Empty** | Editorial headline, an explanation of what a run actually does, example topic chips, and a **specimen card** — a miniature of a real intent breakdown, in the same ink steps and the same mono face the results use. It answers *what will I get?* by showing the answer, and doubles as the class legend. |
| **Running** | Stage label (*Collecting…* → *Reading search intent*), an estimated progress bar derived from `expected_queries × pacing`, elapsed seconds, and Cancel. The bar and the pulsing dot are the only coloured things in the interface. |
| **Results** | Topic as display type, four metrics, the intent-mix bar, then tabs. |
| **Partial** | Info banner with the exact counts and a disclosure listing every failed query. |
| **Rate limited** | Danger alert with a live countdown bar and `mm:ss`; the form stays disabled until it reaches zero. |
| **Error** | Alert with a plain-English title, cause, and a single next action. **Never clears existing results.** |
| **No matches** | Dedicated in-panel empty state naming the filter term. |

### Results detail

- **Metrics** — unique keywords (with per-query density), queries succeeded
  (with a completion bar), source groups, run
  time.
- **Intent mix** — the one piece of real data visualisation. Each keyword is
  counted **once**, under the query type that *first* surfaced it (`types[0]`,
  which preserves discovery order), so the shares total 100%.
- **Intent report** — rendered Markdown at a 68ch measure, with a sticky
  section index built from whatever headings the model actually produced. Wide
  tables get their own scroll container so they never drag the page sideways.
- **Keywords** — grouped by source query (accordions, type tag, count) or flat
  (keyword, its source queries, its type tags). Filter narrows both.

### Market picker

The query bar carries a **Market** selector: which Google to ask. It is a
native `<select>`, restyled rather than rebuilt, so it inherits keyboard
handling, screen-reader labelling and the platform's own wheel picker on a
phone — none of which a custom dropdown gets for free.

It is **populated from `/api/status`**, never hard-coded, so adding a market
is a backend change alone and a stale cached page cannot offer one the server
has since disabled.

Three details that matter:

- **The hint line states what actually changes** — `hl`, `gl` and the ten
  modifier words, shown as chips. The difference between markets is otherwise
  invisible until a run comes back, which is exactly when it is too late.
- **The choice is remembered** in `sessionStorage`, because it is a personal
  working preference rather than shared state. A market the server has since
  disabled can never stay selected: the stored value is validated against the
  live list on every load.
- **Results report the market they ran in**, taken from the response rather
  than from the picker — so a cached result names the market it actually used
  even if the picker has since been changed. It travels into the TXT header,
  the JSON body, the Markdown front-matter and the PDF facts strip.

### Demo mode

`?mock=1` runs the whole UI against `mock-response.json` with no backend and
no API key. Because the value of this tool is that the keywords are genuinely
Google's, **mock data must never be mistakable for a real run**: demo mode
shows a black banner with an orange edge saying so, on every screen, and a
real session never shows it.

Mock mode also stands in a full `/api/status` payload, so every screen — the
market picker included — stays exercisable offline.

### Downloads

Downloads sit **in the tab that owns the data**, not behind one "Export"
menu in the header. The formats differ per tab, and a hidden menu made the
most-used action in the tool invisible. In each group the default format is
filled and the alternates are hairline, so the recommended path is obvious
without the others being hard to find.

| Tab | Formats | Default | Notes |
|---|---|---|---|
| **Intent report** | PDF, Markdown | **PDF** | |
| **Keywords** | TXT, JSON, CSV | **TXT** | |

- **TXT** is the plain keyword list, one per line, under two `#` comment
  lines of provenance — the format the data usually goes straight into (a
  prompt, a spreadsheet paste, a brief), and a naive paste still works if
  the reader strips the comments.
- **JSON** keeps each keyword's `sources` and `types`, which is the part a
  script wants and the flat formats cannot carry without repeating every row.
- **CSV** is written with a UTF-8 BOM. Without it Excel opens non-ASCII
  keywords mojibaked.
- **Markdown** is the report plus a short provenance header, so the file
  still says what it is once it is sitting in someone's notes folder.
- **PDF** is typeset **server-side** by `POST /api/export/report.pdf`. Real
  pagination, running heads and table layout are not things a browser print
  dump gives you, and generating it here would mean shipping a PDF library
  to every visitor. The client posts the report it already holds rather than
  re-running the analysis: a re-run would cost a quota slot and could return
  different prose than the one on screen. If the call fails, a note says so
  and points at the Markdown download, which needs no backend.

## Configuration

One setting, in `config.js`:

```js
window.APP_CONFIG = {
  API_BASE_URL: "http://localhost:8000"
};
```

- `API_BASE_URL` is the **backend service's origin**, no trailing slash. Every
  API call is `API_BASE_URL + "/api/..."`.
- An empty string means "same origin as this page".

**The committed value is the local-development default.** On Render it is
overwritten during the build, so editing this file does not change a
deployment. `build.sh` reads `API_BASE_URL`, strips a trailing slash, promotes
a bare hostname to `https://`, and **fails the build** if it is unset.

## Running locally

The backend must be running first — see [backend/README.md](../backend/README.md).

```bash
cd frontend
python3 -m http.server 5173
```

Open **http://localhost:5173**.

`python3 -m http.server` prints *"Serving HTTP on 0.0.0.0"*, so browsing to
`http://0.0.0.0:5173` is natural. That works: `MODE=dev` accepts any origin,
and `app.js` re-points a loopback `API_BASE_URL` at whatever host served the
page, so reaching the dev server from a phone on the same Wi-Fi works too.

> Use a real HTTP server, not `file://` — that makes the page's origin `null`,
> which CORS rejects and which breaks `sessionStorage`.

### Mock mode — no backend, no API key

```
http://localhost:5173/index.html?mock=1
```

Bypasses the gate and renders `mock-response.json` through the **same code
path** as a real response, after a 6-second delay so the running state is
exercised too.

### If sign-in says "Could not reach the server"

That message covers every failure the browser reports opaquely, so it does
**not** mean the password is wrong. In order:

1. `curl localhost:8000/api/health` → `{"status":"ok"}`.
2. Open the browser console — a failed call logs the API URL it tried.
3. Check the backend log: `OPTIONS /api/login ... 400` is a rejected CORS
   preflight, not a credentials failure.
4. Check `config.js` names the right origin and port.

## Auth

1. The gate posts `{username, password}` to `POST /api/login`.
2. The backend returns `{"ok": true, "access_key": "<token>"}`.
3. **Only the token** goes into `sessionStorage` (`keyword-analyzer.session`) — never
   the password.
4. Every authenticated call sends `X-Access-Key`.
5. Any `401` clears the token through one `clearSession()` helper and returns
   to the gate with an explanation.
6. Sign out clears locally, then calls `POST /api/logout` best-effort.

No `localStorage` anywhere. Every `sessionStorage` access is wrapped, so
private-browsing modes that throw do not break the app.

## Accessibility

- AA contrast across both themes, verified from the tokens.
- Visible focus ring on every interactive element (`:focus-visible`, two-tone
  so it reads on any surface).
- Proper tablist semantics with arrow/Home/End roving; menus close on Escape
  and restore focus; click-outside dismisses.
- `aria-live` on quota, run status and filter counts.
- Skip link; `aria-invalid` on failed fields; scrollable tables exposed as
  focusable regions.
- `prefers-reduced-motion` disables animation and smooth scrolling.
- No horizontal scroll from 320px up — verified at 320/390/834/1024/1440.
- Intent classes are distinguished by ink weight and fill, never by hue, so
  the data reads identically in greyscale and under any colour blindness.
- Each download group is a labelled `role="group"`, so a screen reader hears
  *Download the keyword list* before the three format buttons.

## Safety notes that still apply

- `analysis_markdown` always goes through `marked.parse()` → `DOMPurify.sanitize()`
  before touching the DOM. If either library fails to load, a banner says so
  and the report falls back to `textContent` — **never** raw HTML.
- Client-side run timeout of 180s via `AbortController`; Cancel uses the same
  controller and is distinguished from a timeout.

## API contract

Documented in full in [backend/README.md](../backend/README.md#api-contract).
All calls carry `X-Access-Key` except `/api/login`:

| Call | Purpose |
|---|---|
| `POST /api/login` | `{username, password}` → `{ok, access_key}` |
| `POST /api/logout` | invalidates the token |
| `GET /api/status` | quota, window, pacing, expected query count |
| `POST /api/analyze` | `{topic, market}` → the full result payload |
| `POST /api/export/report.pdf` | the report payload → `application/pdf` |

`mock-response.json` is a valid `/api/analyze` response, and the backend test
suite asserts both that it still validates against the response model and that
every `apiUrl("…")` call site in `app.js` maps to a real route — so the fixture
and the client cannot silently drift from the API.
